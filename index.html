¿Qué es OpenAPI Specification (OAS)?

El estándar internacional agnóstico de lenguaje para describir e interconectar APIs RESTful.

OpenAPI Specification (OAS) es una especificación estándar de formato abierto (escrita en YAML o JSON) que permite describir completamente la estructura de un servicio web HTTP o API RESTful. Permite a humanos y máquinas descubrir y comprender las capacidades del servicio sin necesidad de acceder al código fuente ni a la documentación interna.

Machine Readable
Herramientas automatizadas pueden generar automáticamente clientes SDK, código de servidor, pruebas unitarias y documentación interactiva.
Human Readable
Tanto desarrolladores como arquitectos y analistas pueden leer y diseñar APIs en formato YAML ultra-limpio antes de escribir una línea de código.
Ecosistema Estándar
Respaldado por la OpenAPI Initiative (Linux Foundation) y soportado por gigantes como Google, Microsoft, IBM, Red Hat y SmartBear.
Novedad en OpenAPI 3.1: Integración total y compatibilidad al 100% con JSON Schema Draft 2020-12, soporte nativo para `webhooks` a nivel raíz, e identificadores de licencias usando expresiones SPDX.

Swagger vs. OpenAPI

Aclarando la confusión entre la especificación y el conjunto de herramientas.

Es muy común escuchar los términos "Swagger" y "OpenAPI" usados de forma indistinta, pero representan conceptos diferentes:

Concepto OpenAPI (OAS) Swagger
Naturaleza Es la especificación / estándar abierto. Es un conjunto de herramientas comerciales y open-source.
Propiedad Linux Foundation (OpenAPI Initiative). SmartBear Software.
Ejemplos `OpenAPI 3.0.3`, `OpenAPI 3.1.0`. `Swagger UI`, `Swagger Editor`, `Swagger Hub`.
Función Reglas de sintaxis YAML/JSON para definir el contrato API. Software que lee el documento OpenAPI para visualizarlo o probarlo.

Filosofía API-First

Diseña el contrato antes de escribir el código de backend o frontend.

El enfoque API-First sitúa el diseño de la API en el centro del desarrollo de software. En lugar de desarrollar el backend y luego exportar la documentación (Code-First), se redacta primero el contrato OpenAPI.

Paralelización
Los equipos de Frontend y Backend pueden trabajar simultáneamente usando servidores Mock basados en el archivo OpenAPI.
Menos Errores de Integración
Todas las partes acuerdan los schemas, códigos de respuesta y autenticación antes de implementar la lógica de negocio.

Anatomía de un Documento OpenAPI 3.1

Los campos raíz esenciales para construir un documento OAS válido.

Un documento OpenAPI válido debe contener al menos las secciones `openapi`, `info` y al menos una vía de entrada (`paths`, `webhooks` o `components`).

openapi-base-template.yaml 
openapi: 3.1.0
info:
  title: API de Gestión de Usuarios
  summary: Servicio para administrar cuentas de usuario y perfiles.
  description: Esta API permite crear, listar, actualizar y eliminar usuarios.
  version: 1.0.0
  contact:
    name: Soporte Técnico
    email: soporte@ejemplo.com
    url: https://ejemplo.com/soporte
  license:
    name: MIT
    identifier: MIT

servers:
  - url: https://api.ejemplo.com/v1
    description: Servidor de Producción
  - url: https://staging-api.ejemplo.com/v1
    description: Servidor de Pruebas (Staging)

paths:
  /usuarios:
    get:
      summary: Listar todos los usuarios
      description: Retorna una lista paginada de usuarios activos.
      responses:
        '200':
          description: Lista de usuarios obtenida exitosamente.

Metadatos (`info`) y Servidores (`servers`)

Configura entornos dinámicos y variables de servidor.

Puedes definir múltiples servidores y utilizar variables de servidor con valores permitidos (`enum`) y valores por defecto (`default`).

servers-with-variables.yaml 
servers:
  - url: https://{entorno}.ejemplo.com:{puerto}/v1
    description: Servidor configurable con variables
    variables:
      entorno:
        default: api
        enum:
          - api
          - staging-api
          - dev-api
        description: Subdominio del entorno
      puerto:
        default: '443'
        enum:
          - '443'
          - '8443'

Paths y Operaciones HTTP

Definiendo endpoints, verbos HTTP y detalles de la operación.

Cada ruta en el objeto `paths` puede contener uno o más verbos HTTP:

GET POST PUT DELETE PATCH

paths-example.yaml 
paths:
  /usuarios/{id}:
    get:
      tags:
        - Usuarios
      summary: Obtener usuario por ID
      operationId: getUsuarioById
      deprecated: false
      parameters:
        - name: id
          in: path
          required: true
          description: Identificador único del usuario (UUID)
          schema:
            type: string
            format: uuid
      responses:
        '200':
          description: Usuario encontrado.
        '404':
          description: Usuario no encontrado.

Tipos de Parámetros

Path, Query, Header y Cookie Parameters.

En OpenAPI se admiten cuatro ubicaciones principales (`in`) para los parámetros:

Ubicación (`in`) Obligatorio (`required`) Ejemplo de Uso
`path` true (Siempre obligatorio) `/productos/{categoriaId}`
`query` Opcional (default: false) `/productos?limite=10&pagina=1`
`header` Opcional `X-Request-ID: 12345`
`cookie` Opcional `Cookie: session_id=abcxyz`

Request Body (Cuerpo de la Petición)

Envío de datos JSON, Formularios y Carga de Archivos.

request-body-json.yaml 
paths:
  /usuarios:
    post:
      summary: Crear nuevo usuario
      requestBody:
        required: true
        description: Datos para el registro del usuario
        content:
          application/json:
            schema:
              type: object
              required:
                - nombre
                - email
              properties:
                nombre:
                  type: string
                  example: "Juan Pérez"
                email:
                  type: string
                  format: email
                  example: "juan.perez@ejemplo.com"
      responses:
        '201':
          description: Usuario creado exitosamente.

Respuestas HTTP (Responses)

Mapeo de códigos de estado, cabeceras y formatos de respuesta.

Mapea cada respuesta HTTP usando sus códigos numéricos estandarizados (`200`, `201`, `204`, `400`, `401`, `404`, `500`) o patrones con comodines (`2XX`, `4XX`).

Schemas y Tipos de Datos

Definiendo estructuras de objetos, arrays, primitivos y validaciones.

En OpenAPI 3.1, los Schemas soportan todos los tipos JSON estándar: `string`, `number`, `integer`, `boolean`, `array`, `object`, e incluso arreglos de tipos para valores nulos: `type: ["string", "null"]`.

Composición Lógica: `oneOf`, `anyOf`, `allOf`

Combinando y extendiendo esquemas de datos complejos.

Operador Regla de Validación Uso Típico
`allOf` Debe cumplir con TODOS los schemas especificados. Herencia / Extensión de objetos base.
`oneOf` Debe cumplir con EXACTAMENTE UNO de los schemas. Polimorfismo (Ej: Pago por Tarjeta O por Paypal).
`anyOf` Debe cumplir con AL MENOS UNO de los schemas. Estructuras flexibles de datos combinados.

Reutilización con `components` y `$ref`

Mantén tu código DRY (Don't Repeat Yourself) reutilizando esquemas.

components-ref-example.yaml 
paths:
  /usuarios/{id}:
    get:
      summary: Obtener perfil de usuario
      responses:
        '200':
          description: Éxito
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Usuario'

components:
  schemas:
    Usuario:
      type: object
      required:
        - id
        - email
      properties:
        id:
          type: string
          format: uuid
        email:
          type: string
          format: email

Autenticación y Esquemas de Seguridad

API Keys, HTTP Basic, Bearer JWT y OAuth 2.0.

Define cómo se protegen los endpoints en `components/securitySchemes` y aplica la seguridad globalmente o por endpoint.

Configuración de JWT Bearer & OAuth 2.0

Estructura completa para seguridad avanzada de nivel empresarial.

security-jwt-oauth2.yaml 
components:
  securitySchemes:
    BearerJwt:
      type: http
      scheme: bearer
      bearerFormat: JWT
      description: Ingrese su token JWT con formato "Bearer {token}"

    OAuth2Flow:
      type: oauth2
      description: Flujo de autorización OAuth 2.0
      flows:
        authorizationCode:
          authorizationUrl: https://auth.ejemplo.com/oauth/authorize
          tokenUrl: https://auth.ejemplo.com/oauth/token
          scopes:
            read:usuarios: Leer información de usuarios
            write:usuarios: Crear y modificar usuarios

security:
  - BearerJwt: []
